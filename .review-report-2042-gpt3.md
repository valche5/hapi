## Code findings

### 1. [Minor] Bind the discovered REST port to the serving process

**Changed-line anchor:** `cli/src/opencode/utils/opencodeBackend.ts:399–406`, RIGHT, especially line 406.

**Classification:** `[recommended fix]`. **Confidence:** 95%, based on the selection algorithm, its caller, and the pinned upstream process lifecycle. The concrete scenario is established statically; it was not executed.

**Trigger:** A user has an enabled local stdio MCP server in OpenCode configuration which also exposes an auxiliary loopback HTTP, metrics, or WebSocket listener. That MCP process has started and bound its listener before HAPI scans descendants after `session/new` or `session/load`. For example, the MCP listener is `127.0.0.1:3000` and the OpenCode `serve --stdio` listener is `127.0.0.1:47777`. Both appeared after the initial listener snapshot.

**Defect:** The launcher supplies the entire recursive ACP descendant tree to discovery (`cli/src/opencode/opencodeRemoteLauncher.ts:275–280`). Discovery merges those processes' listeners into an unlabelled set, sorts numerically, and returns the lowest fresh port. Process ancestry establishes that both listeners belong to this launch, but does not establish which one is OpenCode's REST service. The before-snapshot filter cannot distinguish them because both are fresh. It deterministically selects port 3000 in this example.

The password lookup runs independently and prefers the actual `serve --stdio` descendant (`cli/src/opencode/utils/opencodeCompactBridge.ts:350–375`). Consequently, `cli/src/opencode/opencodeRemoteLauncher.ts:282–284` combines the MCP service's port with the OpenCode service's password and records apparently successful discovery. There is no authenticated OpenCode/session probe before enabling `/compact` at lines 389–390.

**User-visible consequence:** `/compact` is advertised as available but its mandatory identity snapshot goes to the unrelated MCP endpoint and fails, so compaction is refused for the session despite a healthy OpenCode REST server. Basic chat can continue. The discovery-failure notice is not emitted because both separately discovered values are non-null.

**Pinned upstream evidence:**

- `packages/core/src/config/plugin/mcp.ts:38–55` loads configured MCP servers into the MCP service.
- `packages/core/src/mcp/index.ts:538–558` starts enabled configured servers during initial reconciliation. Startup is asynchronous, so the relevant condition is a fast MCP process that has bound its socket by the scan; this does not assume every MCP startup has completed.
- `packages/core/src/mcp/client.ts:247–259` creates a local stdio transport, and `packages/core/src/mcp/stdio.ts:84–92` spawns its process on the local execution plane.
- `packages/cli/src/acp/service.ts:141` and `packages/cli/src/acp/catalog.ts:130–146` perform location/catalog setup before the new-session response. Together with the server's startup behavior, configured MCP descendants can already exist when HAPI scans.

**Suggested fix:** Preserve PID attribution when discovering listener candidates and obtain the port and credential from the same identified OpenCode serving process. Alternatively, authenticate and validate the expected OpenCode/session endpoint on each candidate before accepting it. Do not select an arbitrary descendant listener solely by numerical port order.

**Missing regression:** Model `ACP → serve → local MCP`, with both listeners newly bound and the MCP port lower than the serve port. Assert selection of the serve endpoint and its credential. `cli/src/opencode/utils/opencodeBackend.test.ts:484–496` currently asserts that the lowest port across arbitrary owner PIDs wins, so it enshrines the insufficient assumption rather than distinguishing services.

This is independent of the explicitly excluded snapshot-diff fallback race: the ownership scan succeeds, no fallback is used, and both services really are descendants of this ACP launch.

No additional Blocker, Major, or independently actionable Minor finding met the confidence threshold.
